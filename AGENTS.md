# Notes for agents working on isotope

## Names: Isotope, built on Hadron

The project is **Isotope**: the binaries are `isotope-*`, the paths
`/etc/isotope` and `/usr/share/isotope`, the labels `io.kairos.isotope.*`, the
D-Bus name `io.kairos.IsotopeUpdate1`. **Hadron** is only the base distro this
is built on (`ghcr.io/kairos-io/hadron`, `HADRON_VERSION`, the Hadron musl
toolchain, hadron-layers). Do not call a feature of this repo "Hadron". The
naming rules (short form "Isotope, built on Hadron", editions as a suffix,
"Isotope Server") are in the Kairos design system, github.com/kairos-io/design.

The user command is `isotope` (`cmd/isotope/`, installed as `/usr/bin/isotope`):
one binary with a subcommand per job (`upgrade`, `ext`, `recovery`,
`backup`, `restore`, ...). Add a new user-facing command as a subcommand
there, not as a new `isotope-*` binary. `isotope-update`, `isotope-ext` and
`isotope-recovery` are links to it and must keep working: the sessions start
`isotope-update tray`, the menus test for `isotope-ext` and
`isotope-recovery`, and installed systems and people use the old names.
A graphical tool needs cgo and the desktop's libraries, which `isotope` (pure
Go, also on the server) cannot link, so it is its own binary reached through
a subcommand: `isotope welcome` runs `isotope-welcome`, `isotope system`
runs `isotope-system`. The window that manages the machine is "Isotope
System", not "Isotope Settings": on COSMIC it sits next to "COSMIC
Settings", and two "Settings" apps in one launcher are easy to confuse.

Isotope was called Hadron Desktop. The old image repository
`ghcr.io/kairos-community/hadron-desktop` is retired: releases push only to
`ghcr.io/kairos-community/isotope`, and images carry only the
`io.kairos.isotope.*` labels. A system installed before the rename (v0.0.12
or older) still looks for its upgrades in the old repository and finds no new
tag; it moves over once, by hand:
`isotope upgrade --image ghcr.io/kairos-community/isotope:<flavor>-<tag>`.
After that it reads the new repository from its own `/etc/isotope/release`.

These keep such a system working once it has moved; do not remove them
without a plan for those systems:

- `label()` in cmd/isotope/policy.go, which still reads the old
  `io.kairos.hadron-desktop.*` labels of images released before;
- `rootfs/common/system/oem/08_isotope_rename.yaml` (the installer's settings under
  `/etc/hadron-desktop`, the updater's state), the stamps under
  `~/.local/state/hadron*` read by isotope-welcome and isotope-night-light,
  `hadron.unlock` and `hadron.splash.agent` on the kernel command line,
  `themes/hadron` and `hadron/grub2` removed from COS_STATE by
  isotope-grub-theme;
- on the agent: the `hadron_agent` cloud-config key, and the move of
  `/usr/local/.state/var-lib-hadron-agent.bind` in
  isotope-agent-provision.service.

## Repository layout

One Go module at the root (`github.com/kairos-community/isotope`).

- `cmd/<binary>/`: one directory per program. A new program goes here
  (`cmd/isotope`, `cmd/isotope-system`, `cmd/isotope-welcome`,
  `cmd/isotope-install-ui`, `cmd/isotope-install-gui`, `cmd/isotope-agent`).
- `pkg/`: code that more than one program shares (`firewall`, `guikit`, `installer`,
  `isorelease`, `recoverykey`). `cmd/isotope` must stay pure Go, so it must
  not import anything that needs cgo, such as Gio.
- `internal/agent/`: the agent's packages, private to the module.
- `rootfs/common/`: the files every image gets. `rootfs/<variant>/` (sway, i3,
  niri, cosmic, server, agent): the files of one variant.

## Every desktop variant has the same feature set

A variant is one value of `DESKTOP` (today sway, i3, cosmic, niri). The agent
image is an overlay on i3, not a variant, and is exempt where noted. The
server edition (`DESKTOP=server`) is not a variant either and is exempt from
the whole table below: it has no desktop. See "The server edition".

A user who switches variants must find the same Isotope features, reached the
same way. When you add a variant, or a feature that one variant gets, add it to
every variant in the same change, or say in the PR which variants are missing
it and why. A variant whose shell already provides a feature (COSMIC's panel,
Noctalia) uses that instead of an Isotope script, but the feature must exist.

| Graphics drivers and software fallback | Mesa is built twice in the Dockerfile (`mesa` for sway, COSMIC and niri with glvnd; `mesa-x11` for i3 and the agent), with the same drivers per image line. The full line (`GPU=full`) has the x86 set the big distributions ship: GL iris, crocus and i915 (Intel), radeonsi, r600 and r300 (AMD), nouveau (NVIDIA), zink, plus llvmpipe, softpipe, virgl and svga; Vulkan anv, hasvk, radv, NVK (Rust: the `mesa-rust` stage, build time only), lavapipe and venus, with the device-select layer; VA-API (libva, the `libva` stage, DRM and Wayland only) for radeonsi, r600, nouveau and virgl with every codec, and Intel's `iHD_drv_video.so` (the `intel-media-driver` stage, with `libigdgmm` from the `gmmlib` stage; both C++, linked to the image's libstdc++, runtime files and their licences in `/usr/share/licenses/intel-media-driver` and `/usr/share/licenses/gmmlib` only; they are copied into the image in `desktop-default`, not into `/mesa`, to keep the Mesa stages cache keys). The vm line has only llvmpipe, softpipe, virgl and svga, and Vulkan lavapipe and venus. Both lines ship the Vulkan loader (`vulkan-loader` and `vulkan-loader-x11` stages) and the ICD files in `/usr/share/vulkan/icd.d`. Mesa's version is one Renovate PR for both stages (a year-numbered release is never held as a major). Mesa 25.1+ puts the Gallium drivers in `libgallium-<version>.so`, and a driver left out leaves a stub that prints "`<driver>: driver missing`" (svga's is `vmwgfx`, virgl's `virtio_gpu`), which `test/graphics/check-desktop-gl.sh` greps for per line; it also checks each ICD's library, libva and the VA drivers with ldd, and that a Vulkan instance lists lavapipe (`vk-probe.c`). Mesa does not fall back to software when the driver its loader picks from the PCI id is missing or fails (an old Radeon on the vm line, a GPU whose driver crashes): EGL fails and the compositor exits or shows a cursor. So before a compositor starts, `/usr/libexec/isotope-gpu-env` (sourced; safe under `set -e`, once per environment) runs `isotope-gpu-probe` (`tools/isotope-gpu-probe.c`: GBM, EGL on the GBM platform and a GLES2 context on the boot VGA card, as wlroots and smithay pick it, in a child process, Mesa's messages silenced; exit 0 hardware, 1 no working driver, 2 no DRM device; on 1 its line is `<class> <kernel driver>: <reason>`, class `hardware`, `virtual` (a VM's GPU without 3D, or the firmware framebuffer in a VM) or `firmware` (simpledrm or efifb on real hardware: nomodeset, or the driver not loaded; without nomodeset the probe first waits for udev, `udevadm settle --timeout=5`, and looks again, because the live installer can start before the GPU's driver replaces simpledrm)), and on 1 exports `LIBGL_ALWAYS_SOFTWARE=1` (llvmpipe for EGL and GL), `GBM_ALWAYS_SOFTWARE=1` (kms_swrast for GBM: Mesa reads only this one there, and smithay's EGL display and wlroots' allocator are on GBM, so without it a crashing driver still loads), `WLR_RENDERER_ALLOW_SOFTWARE=1` and `ISOTOPE_SOFTWARE_RENDERING=1`, and writes the probe's line to `$XDG_RUNTIME_DIR/isotope/software-rendering`; exit 0 takes the variables back, also from the systemd user manager (exit 2 cleans the manager too; the D-Bus activation environment is not cleaned). The probe's child unsets both software variables, so an inherited flag cannot answer for the hardware. sway's and i3's `start-desktop` source it; niri's session entry is `isotope-niri-session` (`rootfs/niri/usr/share/wayland-sessions/niri.desktop`), which sources it before `niri-session`, so zsh users get it too; COSMIC's session and login screen get it from `/etc/profile.d/isotope-gpu.sh`, because greetd sources `/etc/profile` with `/bin/sh` before every command, and the login screen again from `isotope-greeter-start` (greetd's command, then upstream's `cosmic-greeter-start`). The profile.d file skips SSH logins and root. i3's XLibre runs without glamor by itself; the variables are for its GL clients. `isotope-gpu-notice` (sway and i3 `exec`, niri `spawn-at-startup`, COSMIC `/etc/xdg/autostart`) sends one "Software rendering" notification per session, with the server's own timeout, when the marker exists: on the vm line on a real GPU it points to the standard image (Isotope System, Desktop & image), with the firmware class it names nomodeset, and on a virtual GPU it sends nothing, since software is normal there. Isotope System's About page has a Graphics row: the renderer, or "Software (...)" with the reason (no driver for this GPU, this image has no GPU drivers, virtual GPU without 3D, graphics driver off). The live installer runs cage in software (`WLR_RENDERER=pixman`, the GUI on llvmpipe) when the probe says 1, or once more when cage stops before the first frame, and only then shows the text installer; its first page says why (the same three reasons; nothing on a virtual GPU). `test/graphics/check-gpu-fallback.sh` (CI) checks the scripts and the wiring, `check-desktop-gl.sh` the images. | smartmontools, as on the desktop: `smartctl` and `smartd` (off, `80-isotope-smartd.preset`) from the hadron-layers layer (`SMARTMONTOOLS_LAYER_VERSION`, the Dockerfile `smartmontools` stage) | |
| Docker, as on the desktop: the static bundle, `docker.service` and `docker.socket`, and `92_docker.yaml`, which keeps `/var/lib/docker` on the persistent partition and starts dockerd only on the installed system | |
| the firewall, on by default with SSH (22/tcp) in its default allowed list, as on the desktops (`firewall-default.nft`), off on the ISO; `isotope firewall` over SSH changes it (see Firewall) | |

Its configuration is `rootfs/server/` plus the files the `server-config`
stage names one by one from `rootfs/common/`. A new file in `rootfs/common/` that the server
needs (boot, installer, update service, polkit, firewall) must be added there too. A
server installs only server images and a desktop never installs one
(`Classify` in cmd/isotope/policy.go); `isotope switch` refuses on a server.
`test/server/check-server.sh` checks a built image.

## The Isotope look

Every colour starts in `theme/palette.toml` (roles: base, text, accent,
dim, ..., with `day.*` copies). `tools/gen-theme.py` writes the palette
into every config that has colours, including `theme/cosmic-theme.json`
(COSMIC's theme overlay, from `COSMIC_LOOK` in the script) and the
login screen's two marks. After a palette change, run it, commit the
result, and rebuild. CI runs `--check` and fails on drift or on a
contrast floor.

On COSMIC, `tools/isotope-cosmic-theme` (Rust, the `cosmic-theme` stage)
puts the overlay on libcosmic's own `ThemeBuilder` and writes the dark
and light themes and `Mode` (dark) under `/usr/share/cosmic`. So COSMIC
computes the derived colours itself. Do not hand-edit the theme entries
in the image. Users who already have a theme keep it. To get the new
look they remove `~/.config/cosmic/com.system76.CosmicTheme.Dark*` and
`~/.config/cosmic/com.system76.CosmicTheme.Light*` (the theme and its
builder directories), then log out and in. Do not tell them to use Reset to
default in COSMIC Settings > Appearance: it writes libcosmic's stock theme
into `~/.config/cosmic` and so replaces the Isotope look with stock COSMIC.

The left window buttons come from a libcosmic patch and the CosmicTk key
`window_controls_left`. To turn them off, put `false` in
`~/.config/cosmic/com.system76.CosmicTk/v1/window_controls_left`.
GTK's `button-layout` follows too, but the schema default is not enough:
cosmic-settings-daemon runs `gsettings set ... button-layout` at start and when
the CosmicTk window buttons change, and with no dconf (GLib's keyfile backend)
that user value in `~/.config/glib-2.0/settings/keyfile` beats the default.
`patches/cosmic/cosmic-settings-daemon` makes it write the left layout when
`window_controls_left` is true; `check-look.sh` greps the daemon binary for it.

Flatpak GTK apps on COSMIC follow the look too: xdg-desktop-portal-cosmic
serves only `org.freedesktop.appearance` and text scaling, so
`rootfs/cosmic/usr/share/xdg-desktop-portal/cosmic-portals.conf` lists
xdg-desktop-portal-gtk as a second Settings backend
(`Settings=cosmic;gtk`). xdg-desktop-portal merges the backends and the first
listed wins per key, so the colour scheme still comes from COSMIC (the GTK
backend's own `color-scheme` is the static `prefer-dark` default) while
`button-layout` and `icon-theme` come from the gsettings overrides
(`91_isotope-cosmic.gschema.override`, `90_isotope.gschema.override`). Keep
cosmic first in that line. `check-look.sh` proves the config and the binary,
not that Firefox follows them; that needs a VM with a Flatpak GTK app.

`patches/cosmic/` holds Isotope's changes to COSMIC sources:
`<repo>/*.patch` per repo and `libcosmic/*.patch` for every libcosmic
checkout. `tools/cosmic-build.sh` applies them. Its README lists the
libcosmic revisions each component pins. A new COSMIC epoch must re-check
that table and the patches against the new revisions;
`test/cosmic-build/check-libcosmic-rev.sh` (CI, needs network) fails when the
README table or the `Cargo.lock` of `applets/` and `tools/isotope-cosmic-theme/`
no longer matches the upstream lock at the Dockerfile's `COSMIC_VERSION`.

COSMIC's login and lock screens are one binary, cosmic-greeter: the greeter
runs as the `cosmic-greeter` user, the locker as the logged-in user.
`patches/cosmic/cosmic-greeter/0001` lays out the login screen, `0002` the
lock screen in the same look; the shared pieces (glass buttons, the mark,
the clock, the avatar, the pill field, the scrim) are functions in its
`src/common.rs`, so change them there for both. Both show the soft copy
(`-blur.png`) of Isotope's two wallpapers and a scrim over any other picture.
The lock screen keeps the stock locker's actions (on-screen keyboard,
keyboard layout, suspend). `check-look.sh` greps the binary for a string of
each patch.

`applets/` is a cargo workspace of Isotope's own panel applets:
`isotope-mark` (the mark that opens the Isotope menu) and
`isotope-quick` (quick settings). It is built by `cosmic-build.sh` in
directory mode, so the libcosmic patches apply to it. Its `Cargo.lock`
must stay on the libcosmic revision that cosmic-applets pins (see the
comment in `applets/Cargo.toml`). The panel layout is
`rootfs/cosmic/usr/share/cosmic-layouts/isotope`, which is also the
system default. Isotope Welcome applies it as "Isotope". `applets/` is
GPL-3.0-only (as the greeter patch is), because it builds on COSMIC's GPL
code; the rest of the repository is Apache-2.0.

The icon theme is Conflux, installed whole from its pinned upstream
commit in the `icon-themes` stage, with its GPL licence in
`/usr/share/licenses/conflux`. Do not copy its SVGs into the tree.
`theme/conflux-links.txt` adds aliases for app IDs that Conflux names
differently. `theme/conflux-missing.txt` lists the apps that have no
fitting icon. A dock or first-run app in neither list fails
`test/look/check-look.sh`. CI runs that script on every image and it
checks the whole look in a built image.

## The shortcut sheet is generated

`isotope-help` shows `rootfs/<variant>/usr/share/isotope/shortcuts.txt`, which
`tools/gen-shortcuts.py` writes from the key bindings in the sway, i3 and niri
configs. A binding appears on the sheet only when a `# help: ...` comment
(`// help:` in niri) is on the line above it; see the script's docstring for
`help+:`, `help-section:` and `help-row:`. After you change a binding or its
comment, run `python3 tools/gen-shortcuts.py` and commit the result; CI fails
on a stale sheet. COSMIC's list is hand-kept in `tools/shortcuts-cosmic.txt`.

## Adding a variant

Besides the features above, a variant is wired into the build and release in
these places. Missing one ships a variant that builds locally but is never
released, never upgraded or never checked:

- `Makefile`: `VALID_DESKTOPS`, the help header, `check-boot-ux`.
- `Dockerfile`: its stages, the `DESKTOP` switch, the `kairos` stage.
- `rootfs/<variant>/` for its configuration.
- `.github/workflows/release.yml`: the build matrix (every variant is built
  in both GPU lines, full and vm; COSMIC is in the `build-cosmic` job, which
  waits for the COSMIC prebuilds), the allowed flavors and the expected asset
  counts (two ISOs per variant), the manifest's flavor/line pairs, and the
  public-image check (`<variant>-<tag>` and `<variant>-vm-<tag>`).
- `scripts/release-manifest.sh` (the flavor/line pairs) and `cmd/isotope/release.go`
  (the flavor list).
- The tray updater's "Switch desktop" list.
- `README.md`: the desktop list and the download table;
  `docs/DEVELOPMENT.md`: the variant list and the releases section.
- A design note in `docs/superpowers/specs/`.
